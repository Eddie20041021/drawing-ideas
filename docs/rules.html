CLAUDE.md — 作圖想法筆記

這份文件是給 AI 看的工作規則。讀完之後，你應該知道：使用者丟來一段想法時，要怎麼把它變成一則格式正確的筆記、放在哪裡、怎麼確認沒有出錯。

專案目的

記錄「想畫的畫面」，並且看得出哪些元素已經用過、哪些還沒試過。

使用者用 AI 產圖時，最麻煩的是每次都要重新想背景、服裝、要發生什麼事，也記不得哪些組合畫過了。所以每則想法都拆成固定的四個部分：

部分性質例子
背景具體，只能用詞庫的詞辦公室、街道上、公園內
服裝具體，只能用詞庫的詞正裝、居家服
事件具體，只能用詞庫的詞散步、吃飯
概念不用具體，自由的一句話天氣變冷了、東西弄丟

前三個是畫面上看得到的東西，網站會自動整理出「元素索引」：每個詞用過幾次、出現在哪裡、詞庫裡還有哪些沒用過。概念是這張圖想表達的感覺或主題，可以很模糊，不進詞庫、不統計次數。

網站是給使用者自己看的靈感筆記本，不是作品集。

你最常被要求做的事

使用者會用兩種方式丟想法給你，兩種都要接得住：

一、一句口語的話

下雨天在超商門口等雨停那種感覺，外面很暗裡面很亮

由你拆出背景、服裝、事件、概念。

二、直接給欄位

背景 辦公室　服裝 正裝　事件 吃飯　概念 天氣變冷了

照使用者給的填，不要改詞、不要自己加。沒給的欄位：背景、服裝、事件寫 []，概念寫「待定」；你想到的候選放進 AI 補充。

不管哪一種，原話 都照使用者打的內容原樣保留，然後照下面「新增一則筆記」的步驟走完，最後跑 python3 build.py 確認通過。

目錄結構

路徑內容能不能手動改
notes/<slug>.md公開筆記，一則想法一個檔可以
private/私人筆記與 inbox.md（碎念暫存），已列在 .gitignore可以，但永遠不能上傳
vocab.json元素詞庫，背景、服裝、事件各一個清單可以，照「詞庫規則」
assets/網站的 CSS 與 JS只有改版面時才動
build.py檢查規則並產生網站只有改功能時才動
docs/產出的網站（GitHub Pages 從這裡發佈）不能，一律由 build.py 重新產生
log.md每次修改的紀錄只能往下加，不改舊紀錄

筆記格式

檔案開頭是 front matter，欄位一個都不能少：

---
title: 便利商店門口躲雨
slug: rain-konbini
status: 想法
visibility: 公開
created: 2026-11-10
updated: 2026-11-10
summary: 突然下大雨，主角站在便利商店屋簷下，看著外面發呆。
背景: [便利商店, 街道上]
服裝: [制服]
事件: [躲雨]
概念: 外面很暗、裡面很亮
---
  • title：畫面的名字，10 字左右，講畫面不講技術（「便利商店門口躲雨」，不是「室內外光線對比練習」）
  • slug：小寫英文、數字、連字號，同時也是檔名
  • status：只能是 想法、試畫中、完成、放下 其中一個
  • visibility：notes/ 裡一律是 公開
  • created / updated：YYYY-MM-DD
  • summary：一句話描述畫面，60 字以內
  • 背景、服裝、事件：寫成清單，只能用 vocab.json 裡的詞，用不到就寫 []，不能省略
  • 概念：一句話，不加 [ ]，30 字以內，不能空白（見下方「概念的寫法」）

front matter 之後，段落依序是下面六個，標題文字和順序都不能改：

段落寫什麼
## 原話使用者原本說的話，用 > 引用，一字不改
## 畫面把原話整理成具體的畫面描述：誰、在哪、做什麼、重點是什麼
## Prompt 草稿英文 prompt，放在 ``` 程式碼區塊裡
## 試畫紀錄每次試畫一行，- YYYY-MM-DD：結果與觀察。還沒畫就寫「（還沒畫）」
## 下一步接下來要試什麼，條列
## AI 補充你自己的建議都放這裡

最重要的規則：使用者的想法和你的想法要分開

  • 原話 只能放使用者說的話，不能潤飾、不能補字
  • 畫面 只能整理使用者說過的內容，不能加使用者沒提到的元素
  • 你想到的點子、技巧、替代方案，全部放進 AI 補充
  • 原話太模糊、你需要猜的時候，在 AI 補充 寫「我把 X 理解成 Y，不對請告訴我」，不要直接當成事實寫進 畫面

這條規則存在的原因：筆記本的價值是記錄使用者自己的想法。AI 補的東西混進去，之後就分不出哪些是自己想的。

概念的寫法

概念是「這張圖想表達什麼」，刻意保留模糊，不要把它寫成具體元素。

  • 好的概念：「天氣變冷了」、「東西弄丟」、「等待」、「夏天快要結束了」、「外面很暗、裡面很亮」
  • 不好的概念：「制服女孩在超商躲雨」（這是畫面，不是概念）、「逆光＋背影」（這是技法）
  • 使用者的原話裡如果沒有明顯的概念，從原話裡挑最接近感覺的那幾個字；真的沒有，就在 AI 補充 提一兩個候選，概念 先寫「待定」
  • 概念不進詞庫、不統計次數；元素索引頁的最下面會列出所有概念，方便回頭看自己常想畫什麼

詞庫規則（vocab.json）

背景、服裝、事件 只能用 vocab.json 裡有的詞，build.py 會擋下不在詞庫的詞。

  1. 先找詞庫裡有沒有意思相同的詞，有就用既有的，不要新造同義詞（已經有「黃昏」就不要再加「夕陽」）
  2. 真的沒有，才把新詞加進 vocab.json 對應的維度，加在清單最後
  3. 一個詞只放在一個維度。拿不準時這樣分：
  • 背景：在哪裡，寫地點（「辦公室」、「公園內」）。天氣、時間不進背景，寫在畫面描述裡
  • 服裝：穿的是哪一類衣服（「正裝」、「居家服」）。雨傘、包包這類配件不進詞庫，寫在畫面描述裡
  • 事件：畫面裡正在發生的事，包含人物的動作（「吃飯」、「散步」、「回頭」）
  • 看了會有什麼感覺、想表達什麼，那是概念，不是元素，不要加進詞庫
  1. 詞要短，2～5 字。粒度以使用者自己給過的詞為準：背景是「辦公室」這種地點，服裝是「正裝」這種類型，不要細到單一品項或顏色
  2. 不刪除詞庫裡的詞，就算沒有筆記在用。元素索引會把它列在「還沒用過」，那本來就是用來找靈感的

公開分級

GitHub 上的內容任何人都看得到，所以預設是私人。

  • 使用者沒有明講「公開」，新筆記一律放 private/，visibility: 私人
  • 只有使用者明講要公開，才放 notes/
  • 從私人改成公開之前，先做「公開前檢查」：
  • 不能出現使用者經營中的原創角色名字或專屬設定，公開筆記一律用「主角」稱呼
  • 不能出現真人名字、學校、地址等個人資訊
  • 不能在 prompt 裡用在世畫師的名字當風格
  • 圖片只能放使用者自己產生的圖，不能放別人的作品
  • 任何情況下都不能把 private/ 的內容複製、摘要或引用到 notes/、docs/、log.md 或 commit 訊息裡

Prompt 草稿規則

  • 英文，一段話或逗號分隔都可以
  • 順序：主角與服裝 → 事件 → 背景 → 最後用一兩個形容氣氛的詞帶出概念
  • 概念不要直譯成 prompt（模型看不懂「夏天快要結束了」），改成畫面上看得到的暗示，寫在 AI 補充 讓使用者挑
  • 不寫在世畫師的名字、不寫真人名字、不寫作品或角色的名字
  • 已知會出錯的地方（例如回頭角度容易畫過頭），解法寫在 AI 補充，不要直接塞進 prompt

狀態怎麼改

狀態什麼時候用
💡 想法剛記下來，還沒畫
🎨 試畫中至少畫過一次，還在調整
✅ 完成使用者說滿意了
🗄 放下使用者說先不畫了。保留筆記，不要刪
  • 每次改狀態或加試畫紀錄，都要把 updated 改成當天
  • 試畫紀錄 只能往下加，不能改寫舊的紀錄，失敗的紀錄也要留著
  • 狀態由使用者決定，你不能自己把想法標成「完成」

圖片

  • 放在 assets/notes/<slug>/，檔名用 01.webp、02.webp 依序編號
  • 在 試畫紀錄 那一行後面用 ![描述](../assets/notes/<slug>/01.webp) 插入
  • 單張 500 KB 以內，太大先壓縮

新增一則筆記的步驟

  1. 讀使用者的原話，決定 title、slug、summary
  2. 把原話拆成背景、服裝、事件，每個詞都先對照 vocab.json（照詞庫規則）；再寫一句概念（照概念的寫法）
  3. 問自己：使用者有沒有說要公開？沒有就放 private/
  4. 照「筆記格式」寫檔，原話一字不改
  5. 跑 python3 build.py
  6. 建置時如果出現「可能重複」，在 AI 補充 寫出跟哪一則很像、差在哪裡，讓使用者決定要合併還是分開
  7. 在 log.md 最下面加一行
  8. 跟使用者回報：新增了哪一則、用了哪些新詞、有沒有疑似重複

修改既有筆記時一樣要做第 5、7、8 步。

建置與檢查

python3 build.py

只用 Python 標準函式庫，不需要安裝任何套件。它會檢查：

  • 每個欄位都有、格式正確、檔名等於 slug
  • 狀態是四種之一，日期格式正確，updated 不早於 created
  • 背景、服裝、事件的詞都在詞庫裡；概念是一句話、不空白、30 字以內
  • 六個段落都在，順序正確
  • notes/ 裡沒有私人筆記
  • slug 不重複

有任何一項沒過，它會列出原因並停止，docs/ 不會更新。不要為了讓建置通過而去改 build.py 的檢查，要改的是筆記本身。通過後會產生首頁、每則筆記的頁面、元素索引，以及這份規則的網頁版。

網站風格

  • 乾淨、極簡、大量留白，重點是文字
  • 所有顏色都定義在 assets/style.css 的 :root 變數裡，新樣式沿用變數，不另外寫死顏色
  • 狀態顏色固定：想法黃、試畫中紫、完成綠、放下灰
  • 概念一律用斜體淡色顯示，跟具體元素的標籤區分開
  • 支援深色模式（跟隨系統設定），手機版也要能正常閱讀
  • 不加動畫、不加外部字型、不引入任何外部 JavaScript 函式庫

log.md 格式

- 2026-11-10 新增 rain-konbini（想法）；詞庫新增：背景「街道上」

一次修改一行，寫做了什麼、動到哪些詞。不寫私人筆記的內容。

不能做的事

  • 手動修改 docs/
  • 把 private/ 的任何內容放到會上傳的地方
  • 修改或潤飾 原話
  • 刪除筆記、刪除詞庫裡的詞、刪除舊的試畫紀錄
  • 替使用者決定狀態
  • 為了通過建置而放寬 build.py 的檢查
